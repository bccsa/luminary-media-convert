# Player contract and conventions (detail)

For `player-core`, `player-web`, `hls-core` and the native adapters. See also `docs/suspension-safe-playback.md`, `docs/chunk-warming.md`, `docs/encrypted-sidecar-format.md`.

### `luminary://key` and the client-side player contract

Encryption keys are generated locally (`randomBytes(16)`) and never leave the machine, so there is nothing to serve them over HTTP. When no explicit `keyUrl` is configured, `#EXT-X-KEY` is written with the sentinel URI `luminary://key` (`LUMINARY_KEY_PLACEHOLDER_URI`, exported from `@luminary-media-converter/hls-core`).

A Luminary player is therefore expected to:

1. Fetch the master and media playlists, decrypting LMCENC-wrapped ones (an encrypted session encrypts its playlists and sidecars too, unless it opted out).
2. Supply the key for `luminary://key` (and any other AES-128 key URI — a locally supplied key always wins). The wrapper normalizes key URIs to the sentinel and the engine adapter serves the raw bytes **from memory** (the VHS xhr seam on the web; `AVAssetResourceLoaderDelegate` / ExoPlayer `DataSource` later) — a key blob URL is only the fallback for adapters without a key hook.
3. Feed the munged playlists to the engine. **`player-core` (`PlayerController` + pipeline) is the reference implementation**, with `player-web`'s `HlsJsVideoAdapter`/`LuminaryPlayer` as the web engine binding — which both the media encoder app and the Luminary app consume.

The encoder writes **one** spec-correct multi-angle `master.m3u8`: each camera angle is an `#EXT-X-MEDIA:TYPE=VIDEO` rendition group and every `#EXT-X-STREAM-INF` carries `VIDEO="<group>"`. Most players ignore video rendition groups and simply play whichever variant their ABR logic picks, so narrowing happens client-side with the `hls-core/` helpers — this is the contract, not an implementation detail:

- `listVideoAngles(masterText)` → `{ id, name, isDefault }[]` (empty for a single-angle master)
- `extractAnglePlaylist(masterText, angleId)` → a master pinned to one angle; returns the input unchanged when there is nothing to narrow, so it is safe to apply unconditionally
- `extractAudioOnlyPlaylist(masterText)` → an audio-only master, one variant per audio `GROUP-ID`, or `null` when there are no audio groups

## Key Conventions (player)

- **The line between `player-core` and an adapter is what must keep working while JavaScript is frozen.** A native engine keeps pulling segments from its own threads while a locked screen suspends the WebView, so anything that acts *during* playback belongs beside the engine. `player-core` keeps munging, quality capping, angle switching, coming-soon polling, chapters/subtitles and the state store — none of which run during playback, or matter if they pause. Adapters own stall *detection* (hls.js's gap controller, VHS's `PlaybackWatcher` in the retired player, the native players all watch their own buffer; a wrapper timer sampling `currentTime` cannot tell a slow request from a wedged decoder, and the one `player-core` used to run made stalls worse — it is gone, surfaced instead as the `stalled` adapter event), the recovery ladder (engine primitive → bounded `reattach()` with backoff on a MONOTONIC clock → `reload-requested`) and chunk warming. `docs/suspension-safe-playback.md` is the normative spec a native adapter implements against and `player-web/src/drivers/` is what it ports; `reattach()` is separate from the re-munge because the munge is deterministic for an unchanged selection (a reload produced byte-identical playlists behind fresh URLs, so only the engine being rebuilt ever mattered), which is what lets a backgrounded player recover without waking JavaScript. Implementing apps talk to `PlayerController` only. There is no munge fast path: every source — encrypted or not — fetches and rewrites its media playlists, so behavior never depends on what the source happens to be
- Chunk warming splits along the same line: `player-core` builds the boundary schedules (`buildChunkSchedules`, pure, serializable) and owns the policy (`PlayerControllerOptions.prefetch`); the pacing loop is adapter work via the optional `warmChunks` contract, because a JS interval is throttled in the background exactly when a native player keeps playing. `docs/chunk-warming.md` is the normative spec a native adapter implements against
- Quality capping is **load-time only**: `PlayerSource.maxHeight` munges higher renditions out of the playlist; a playing video keeps its old cap until the next `load()`. Selecting the `Audio only` pseudo-angle (`AUDIO_ONLY_ANGLE_ID`) plays a munged master with zero video variants — no video bytes are downloaded
- LMCENC (`docs/encrypted-sidecar-format.md`) is the only sanctioned way to encrypt playlists/VTTs; detection is by magic prefix, never by absence-sniffing, and plaintext assets keep working when a key is configured
- **VOD is read once, and that is what makes it suspension-safe**: the wrapper munges at load and hands finished text to the `ServeStrategy`, so JavaScript is off the request path for the rest of playback. A LIVE playlist (no `#EXT-X-ENDLIST`) breaks that — re-fetched, re-decrypted and re-rewritten every target-duration — so the refresh belongs to the serving layer, which declares the capability by implementing `serveLive(spec)`. Its absence makes the pipeline refuse a live source (`PlayerError{ code: 'live-unsupported' }`) rather than serve a snapshot frozen at its first read. `LivePlaylistSpec` is plain data so a native resolver does the whole job unaided, and `resolveLivePlaylist` (fetch → LMCENC sniff → `rewriteMediaPlaylist`, one read per engine request, no timer — the engine's own refresh drives it) is the step it ports. `player-web` implements it: `BlobServeStrategy.serveLive` mints `luminary://live/<n>` and the hls.js playlist loader in `hlsLoaders.ts` answers the engine's requests for it. The frozen `player-web-old` (hls.js) does not, and refuses live. Nothing here *produces* live output (`-hls_playlist_type vod`); live sources are third-party
- `rewriteMediaPlaylist` is deliberately **string work, not a model round-trip**: it makes two edits (substitute the key URI, absolutize URIs), it is strictly more preserving that way (a line it does not recognise is untouched rather than rebuilt from a model), and it is the one rewrite on live's per-request path, so it is what gets ported to Swift and Kotlin. `hls-core`'s lossless model stays where it earns its keep — the load-time master munge, and the API's own playlist building
